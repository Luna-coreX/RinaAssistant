Задача плана 4.0-I05.

Рина — две программы. Это меняет отладку сильнее, чем кажется: половина может умереть молча, и вторая будет ждать ответа, которого не будет никогда. Оба аудита 3.0.0 воспроизводили проблемы в песочнице, потому что журналов не существовало вовсе.

Сначала — регресс

python tools/regress.py

Один вызов, один отчёт: 39 проверок примерно за две минуты, код возврата 1 при любом провале. Если сломалось что-то общее, регресс скажет это раньше, чем вы начнёте искать руками.

python tools/regress.py --group провод      # только протокол
python tools/regress.py --list              # что вообще есть

Что трогает машину — говорит вслух, водит мышью, заводит значок в трее — отделено и не запускается посреди рабочего дня без спроса.

Журналы

%APPDATA%\RinaAssistant\logs\
    rina.log        всё подряд, оба слоя
    security.log    запуски, плагины, опасные действия, обновления

security.log общий у ядра и оболочки: две хронологии на одно происшествие пришлось бы сшивать руками по времени, и первая же несостыковка часов сделала бы это невозможным.

Формат:

2026-09-08 14:05:11 INFO    t-9f2c41ab8e01  rina.engine   команда принята

Третье поле — сквозная трассировка (4.0-D15). Она и есть главный инструмент отладки двух процессов.

Трассировка

trace_id рождается там, где началось действие — нажатие в оболочке или распознанная фраза, — и переносится во все сообщения, порождённые этим действием, включая события и ошибки, через границу процессов.

Без неё в двух журналах лежат два несвязанных набора строк, и вопрос «что произошло после того нажатия» отвечается сверкой отметок времени, то есть догадкой.

# всё, что случилось из-за одного нажатия — в обоих слоях сразу
findstr t-9f2c41ab8e01 "%APPDATA%\RinaAssistant\logs\rina.log"

Прочерк - вместо трассировки — не ошибка: так помечено то, что никем не вызвано (запуск, сработавший сам по себе таймер).

Подробность и приватность

Настройки → Диагностика → Подробность журнала    ERROR … DEBUG
                        → Записывать тексты реплик

По умолчанию вместо текста реплики пишется её длина: этого хватает отличить «пустой ввод» от «10 000 символов» и не хватает прочитать разговор. Поэтому журнал можно прикладывать к сообщению об ошибке.

Тексты пишутся только при явно включённой log_texts и только на уровне DEBUG. В security.log текста команды нет никогда, даже при включённой настройке: «что запускали» и «что человек сказал» — разные сведения.

Диагностический пакет

О программе → Диагностика → Собрать пакет

Журналы обоих слоёв, версии, состояние связи и настройки — в один архив. Свободный текст, пути и адреса заменены длиной; истории разговора и команд там нет. Что именно вошло — написано внутри пакета первой строкой, вместе с ответом на вопрос, была ли включена запись текстов.

Запустить половину отдельно

Только ядро

python rina_core.py --transport stdio

Режим stdio — ответ на единственную цену именованного канала: у канала нет ни netstat, ни перехвата пакетов. Стандартный ввод-вывод не слушающая точка, к нему нельзя подключиться снаружи, и он живёт ровно столько, сколько живёт процесс. Отладка получается, дыры не появляется.

Ядро можно поднять под песочницей, чтобы оно ничего не сделало с машиной:

python tools/_core_sandboxed.py --transport stdio

Только оболочка

Оболочка поднимает ядро сама. Если ядро не поднялось, она всё равно работает и честно говорит об этом в подвале колонки: окно, трей и хоткеи принадлежат ей и обязаны работать, даже если чужой процесс упал.

Режимы самопроверки оболочки

Оболочка умеет проверить себя и нарисовать себя в PNG.

dotnet run --project shell/Rina.Shell -- --check-core
dotnet run --project shell/Rina.Shell -- --shot окно.png --section settings
dotnet run --project shell/Rina.Shell -- --shot окно.png --finish silver
РежимЧто проверяет
--check-coreподнимается ли настоящее ядро и жива ли связь
--check-pagesзаводится ли команда и напоминание из окна
--check-platformсистемный слой: индекс, подписи, запреты, журнал
--check-voiceядро синтезирует, оболочка играет — вслух
--check-audioзвук ходит в ядро и обратно, кредит соблюдается
--check-trayтрей возвращает окно, а не роняет программу
--check-confirmу вопроса есть срок, но не у всякого
--check-motionдвижение видно во времени, а не на снимке
--check-hoverнаводка действительно меняет цвет
--check-diagnosticsпакет собирается и не увозит лишнего
--check-updatesметаданные, целостность, журнал обновлений
--check-overlaysреплика и плашка «слушаю» поверх экрана

Снимок делает тот же код, что рисует настоящее окно, — поэтому по нему можно сверять цвета с токенами:

python tools/check_shell_render.py окно.png silver

Частые случаи

«Ядро не отвечает». Смотрите подвал колонки — там состояние связи и номер попытки. Дальше rina.log: ядро пишет причину, по которой не поднялось, чаще всего это интерпретатор без нужных пакетов. Оболочка берёт Python из окружения проекта, если оно есть, и только потом из PATH: голоса и модели стоят в окружении, и ядро, поднятое «просто питоном», честно сообщит, что движков нет.

«Она молчит». Три места по очереди: движок синтеза в настройках, кнопка «Проверить голос» рядом с ним, --check-voice. Ядро без оболочки молчит намеренно — у процесса, который может работать сервисом, не должно быть своего голоса.

«Не слышит». Кнопка «Проверить микрофон» отвечает на «слышно ли вас вообще», а не «понимает ли она слова»; это разные вопросы, и первый закрывает большинство жалоб.

«Настройка не сохранилась». Проверьте, что ядро её приняло: ответ на settings.set содержит вердикт по каждому ключу, а не одно «получилось» на всю посылку.

«Плагин ничего не делает». security.log скажет, загрузился ли он и почему нет. Плагин версии старше 4 не загружается, и причина названа словами.

Записанные сессии

Golden-набор проверяет фразы, но не ловит того, что копится во времени: протухший вопрос, подтверждение, снятое посторонней репликой, цепочку из нескольких шагов.

python tools/session.py --list
python tools/session.py --replay docs/golden/sessions/confirm-expired.json

Промежутки записаны явно, поэтому воспроизведение не ждёт минуту по-настоящему: часы подменяются.
