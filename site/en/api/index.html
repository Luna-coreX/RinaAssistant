Where to start

If you want to give Rina a new skill — a command, a tab, a tile on the home screen — you need the plugin API. A plugin is a folder in plugins/ with a plugin.json manifest and a main.py holding a class that inherits from Plugin.

If you want to replace the shell — write your own interface, your own voice client, your own integration — you need the protocol. The core runs as a separate process and speaks over a named pipe; everything the program can do is expressed as methods and events.

The governing rule of both surfaces is the same: a plugin declares. It hands over a description of its tools and of its page, and the core decides when to call and when to show them. That is why the shell can be rewritten whole: a plugin holds no line of its code — no widgets, no markup, no calls into the window.

}

Hooks

All of them are optional. Leave one alone and Rina behaves as if it did not exist.

HookWhen it is called
on_enableThe plugin was switched on. Set up your own things here: a schedule, a cache, a connection.
on_disableSwitched off. Close here whatever you opened.
on_commandA phrase arrived. Return True and it is yours; nobody parses it further.
on_eventAn event of the core happened: a name and some data.
toolsA list of PluginTool — what the plugin can do. Read when it is enabled.
pageA description of your own tab as a list of elements. Empty means no tab.
homeA description of a tile for the home screen. Empty — and that is the right answer for most.
on_actionA button on your page was pressed. The page is rebuilt afterwards by itself.
settings_schemaA description of your settings; Rina assembles the panel herself.

The home tile is drawn often and has to be short: build it from what you already know, and go to the network on your own schedule, answering from memory. A tile that grows is a page, and there is already a place for a page.

Tools

A tool is what the plugin can do. It goes into the core's shared registry under the name plugin.<id>.<name> and gets exactly the same gates there as a built-in one: the permission check, confirmation of the irreversible, and a journal entry naming which plugin started it.

FieldMeaning
nameA short name inside the plugin; the core adds the prefix itself.
summaryOne line: what the tool does.
runThe function the core will call. The plugin never calls it itself.
paramsThe arguments, by the same Param the built-in tools use.
permissionsWhat has to be allowed. Empty means nothing.
confirm_requiredAsk the person on every call.

Permissions are checked before registration: what a plugin is not entitled to is not granted, and the tool itself is not created. A tool without the permission it needs would refuse anyway — but only after the person had seen it and called it.

Permissions

The catalogue is one, shared by the core and by plugins. A second catalogue "for plugins" would mean two languages about one and the same thing and an inevitable divergence — "network" here and "internet" there. But not all of it is available.

NameWhat it allowsTo a plugin
process.launchOpen the applications and folders you name.granted
system.mediaChange the volume and control the player.granted
system.lockLock the desktop on command.granted
system.powerShut down, restart and sleep the computer.never
screen.captureTake a screenshot and save it.granted
network.localAsk the language model running on this computer.granted
network.externalReach services outside this computer.granted
files.readRead the files you pointed at.granted
files.writeCreate and change files.never
screen.readSee what is on the screen. Created in advance, for 5.0.never
input.synthesizeClick and type on your behalf. Created in advance, for 5.0.never

The four refusals are not about distrusting you; they are about what a plugin must not be able to do by construction: shutting the computer down at somebody else's code's decision is not what a weather plugin is installed for, and writing files would mean somebody else's name in a person's directories. The last two belong to 5.0 and hang on no tool at all yet.

A refusal here is an answer: the person sees exactly what the plugin was not given, and why.

Page vocabulary

A plugin's page is described as data. No widgets, no markup: you return a list of elements and the shell — whichever one is installed — draws them. Schema version two, thirteen kinds.

KindWhat it is
titleA section heading.
textOrdinary text.
noteA smaller, quieter explanation.
itemsA list of lines.
buttonA button with an action; the press arrives at on_action.
inputAn input field with a placeholder and a button.
tableA table of rows and, if needed, a header.
progressA progress bar from zero to one.
badgeA short state label.
dividerA separator.
cardA container with a title.
groupA group of elements.
rowA row: elements side by side.

An unfamiliar kind is shown visibly and by name: a plugin may be built for a newer schema, and skipping it silently would make part of its page invisible without a trace.

Settings

The same way: you describe the fields and Rina builds the panel. Four kinds.

KindWhat it is
toggleA switch: yes or no.
textA line of text.
choiceOne of a set.
sliderA number within bounds, with a step.

A whole example

A plugin that declares one tool, answers a phrase and shows its own page. main.py beside the manifest from the first section.

# plugins/weather/main.py
from plugins.api import Plugin, PluginTool
from plugins.page_spec import Title, Text, Note, Button
from plugins.settings_spec import Text as TextField, Toggle


class WeatherPlugin(Plugin):

    def on_enable(self):
        self.log("weather is on")

    def tools(self):
        return [PluginTool(
            name="current",
            summary="Tells the weather in the chosen city",
            run=self._current,
            permissions=("network.external",),
        )]

    def _current(self, args):
        city = self.setting("city", "London")
        return {"text": f"It is clear in {city} right now"}

    def on_command(self, text):
        if "weather" not in text.lower():
            return False
        self.respond(self._current({})["text"])
        return True

    def page(self):
        return [
            Title("Weather"),
            Text(f"City: {self.setting('city', 'London')}"),
            Note("Refreshed on request, at most once in ten minutes."),
            Button("Refresh", action="refresh"),
        ]

    def on_action(self, action, value=None):
        if action == "refresh":
            self.respond(self._current({})["text"])

    def settings_schema(self):
        return [
            TextField("city", "City", default="London"),
            Toggle("speak", "Say it aloud", default=True),
        ]

The folder goes into plugins/. On installation the name is checked, the folder must land inside plugins/, Windows device names are rejected, and replacing an already installed plugin forcibly switches it off.

Compatibility

The manifest states the API version the plugin is written for. The range that loads is four to four: the lower bound deliberately coincides with the current one, because a plugin that hands over a ready-made widget cannot be "partly supported" — a C# shell will not draw a Python widget in any way at all.

A mismatch does not stay quiet. The person is told the reason, the version and what to do: update Rina if the plugin is newer, or update the plugin if it is older. A silent "the plugin simply does not work" looks like a breakage in Rina when what is outdated is the plugin.

Protocol: channels

The shell is the C# process: the window, the output devices, launching programs. The core is the Python process: the decisions. The shell starts the core, watches it and restarts it; the core connects as a client.

ChannelNameContents
control\\.\pipe\rina.<session>.controlJSON messages
data\\.\pipe\rina.<session>.databinary frames

They are separate so that a burst of audio never holds a control message behind it. A control frame is four bytes of length and a UTF-8 JSON payload, with a 1 MiB limit per message. A data frame is a length, a stream id, a sequence number and bytes, with a 256 KiB limit.

Binary data is never encoded inside JSON: base64 inflates it by a third and makes audio share a queue with control.

Protocol: envelope

Nine fields, and they are present in every control-channel message without exception.

FieldMeaning
vThe protocol version — the highest common one, chosen at the handshake.
typerequest, response, event or error.
idThe message's identifier, unique within the session.
methodThe name of the method or event — for a request and an event.
correlation_idThe request's id — for a response and an error.
stream_idThe stream this message belongs to, if it belongs to one.
timestampThe time of sending, seconds since the epoch.
trace_idEnd-to-end tracing.
payloadThe contents; an empty object when there is nothing to say.
 
{
  "v": 1,
  "type": "request",
  "id": "s-0042",
  "method": "command.handle",
  "timestamp": 1756750000.123,
  "trace_id": "t-8f21",
  "payload": {"text": "запусти телеграм", "source": "typed"}
}

An unknown method in a request is the error protocol.unknown_method. An unknown event the receiver silently ignores. The asymmetry is deliberate: a missed request is a lost action, a missed event is a lost notification.

Protocol: contract

Everything that can be asked and heard is machine-readable — contract-v1.json. Both sides are checked against it; the C# half of the protocol is generated from it.

Of whatHow manyFor example
methods68command.handle, apps.launch, reminders.add
events23listening.started, assistant.response, reminder.fired
errors30permission.denied, app.not_found, confirmation.required
capabilities20audio.input, reminders, plugins
stream kinds3audio.input, audio.output, screen.frame

The first message of a session is the handshake: both sides name the versions they support and their capabilities, and the highest common version is chosen. Before it, any other method answers with protocol.not_ready.

Half of what is described goes unused in 4.0, and that is deliberate: adding it later costs a rewrite on both sides, while laying it down now costs a paragraph in a document. The full text is PROTOCOL-v1.md.

What is never granted

A separate process is not a sandbox, and that has to be said plainly. The same interpreter, the same user rights; subprocess works inside a plugin. What a plugin lost is access to the application; access to the machine was never taken from it.

What the split does give: a plugin's tools go into the same registry and get the same gates; some permissions are never granted, and a tool asking for one is not created at all; a plugin can turn to the core for exactly two things; a call has a deadline, one that does not answer is killed, and its neighbour is left intact.

So install plugins the way you install any other code: looking at whose it is. The full description of the boundaries is SECURITY.md and the threat model.
