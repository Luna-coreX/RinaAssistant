# План 3.1.0 — промежуточный этап перед 4.0.0

**Цель:** закрыть всё известное открытое по безопасности, гонкам и отзывчивости, пока код ещё на Python и проверяется целиком. После разделения на два процесса каждая из этих правок стоит дороже, а часть станет невоспроизводимой.

**Правило версии:** новых пользовательских возможностей нет. Исключение одно — логирование, потому что без него следующий аудит нечем подкрепить.

**Источники:** внешний аудит Perplexity от 31.08.2026 (взято то, что подтвердилось проверкой по коду), собственный аудит 3.0.0 (раздел «Известные ограничения»), и одна находка, всплывшая при проверке чужих утверждений.

Каждый пункт ниже сверен с текущим кодом — с указанием файла и строки на момент составления плана.

## Блок S — Безопасность

**3.1-S01 · Убрать `shell=True` и запуск по короткому имени** — S — нет
`voice/commands.py:62` — `subprocess.Popen(app["win"], shell=True)`. Инъекции нет: строки берутся из константы `APPS`, пользовательский ввод туда не попадает. Проблема в другом — запуск идёт по короткому имени (`discord`, `calc`, `notepad`, `explorer`, `start chrome`), а порядок поиска Windows включает текущую папку, поэтому подложенный туда файл выполнится вместо системного. Тот же класс, что был у `shutdown.exe` в `system_control.py`.
Решение: снять `shell=True`, передавать список аргументов, системные утилиты резолвить через уже написанный `system_control.system_exe()`, остальное — через `app_index`, который знает реальные пути.
*Готово когда:* во всём проекте нет ни одного `shell=True`, и запуск встроенных приложений не зависит от текущей рабочей папки.

**3.1-S02 · Проверять цель перед запуском** — S — нет
`voice/app_index.py:567` (`launch`) и `voice/user_commands.py:199` (`_open_path`) вызывают `os.startfile()` без единой проверки. Стало заметно из-за кэша: индекс живёт сутки, программу за это время могли удалить.
Решение: перед запуском проверять существование пути; при отсутствии — внятный ответ («Не нашла программу по этому пути») и пометка записи в кэше как устаревшей.
Сознательно **не делаем** белый список каталогов, который предлагал внешний аудит: он ломает portable-программы вроде `C:\renpy-8.5.3-sdk`, а это заявленная возможность.
*Готово когда:* удалённая программа даёт понятный ответ, а не системную ошибку.

**3.1-S03 · Честный результат запуска приложений Магазина** — S — нет
`voice/app_index.py:570` возвращает `True` безусловно: `explorer.exe` завершается сразу и о судьбе `shell:AppsFolder\<id>` ничего не сообщает. Несуществующий идентификатор отчитывается успехом, и в последовательностях шаг считается выполненным.
*Готово когда:* неверный AppUserModelID не отчитывается как успех.

**3.1-S04 · `SECURITY.md`** — S — нет
Как сообщить об уязвимости, что считается уязвимостью, чего ждать по срокам. Плюс раздел о границах доверия: плагин — это произвольный код в процессе приложения, и пользователь должен это знать до установки.

## Блок R — Гонки и состояние

**3.1-R01 · Очередь воспроизведения речи** — M — нет
Две проблемы, лечатся одним решением.
Первая: фиксированные имена временных файлов — `rina_gtts.mp3`, `rina_edge.mp3`, `rina_piper.wav` (`voice/tts.py:173,289,361`). Два ответа подряд затирают файл друг друга.
Вторая: общий флаг `_speaking` — один `threading.Event` на всё ядро (`core/engine.py:52`), поэтому перекрывающиеся ответы не выстраиваются, а мешают друг другу.
Решение: один воркер воспроизведения с очередью; каждый синтез пишет в собственный файл с уникальным именем; файл удаляется после успешного проигрывания; ошибки чтения не роняют воркер.
*Готово когда:* три ответа подряд проигрываются по очереди целиком, ни один не обрывается и ни один временный файл не остаётся.

**3.1-R02 · Глубокая копия `DEFAULTS`** — S — нет
`core/settings_store.py:138,153,371` — `self._data = dict(DEFAULTS)`. Копия поверхностная, а `DEFAULTS["plugin_settings"]` (строка 92) — изменяемый словарь. Настройка любого плагина пишется в общий словарь по умолчанию, из-за чего `reset()` восстанавливает уже испорченное значение, а не заводское.
*Готово когда:* после настройки плагина и `reset()` значение по умолчанию совпадает с заводским.

**3.1-R03 · Атомарные обновления хранилищ** — M — нет
`voice/history.py:48` (`add`), а также `ReminderStore.mark_done` и `bump_stat` устроены как чтение-изменение-запись: `entries = self.all()` → изменить → записать. Блокировка в `SettingsStore` защитила запись файла, но не эту последовательность: два потока читают одно состояние и один затирает изменения другого.
Решение: выполнять чтение-изменение-запись под общей блокировкой хранилища.
Полный переход на SQLite, который предлагал внешний аудит, — **не в этой версии**: 5.0-B01 всё равно заводит SQLite, а 4.0-I02 будет мигрировать данные, и делать миграцию дважды незачем.
*Готово когда:* параллельная запись из нескольких потоков не теряет записи в нагрузочном тесте.

**3.1-R04 · Кнопки проверки не зависают** — S — нет
`voice/mic_tester.py:33` — `_worker` без `try/finally`: если `test_microphone` бросит исключение, `_busy` навсегда останется `True`, сигнал `finished` не придёт, кнопка «Проверить» останется серой до перезапуска. Рядом лежит правильный образец — `voice/voice_tester.py:37-42`.
Та же схема нужна кнопке «Проверить связь» для модели: `http.client.HTTPException` не входит в перехватываемые `core/llm.py:94-97`.
*Готово когда:* исключение в фоне возвращает кнопку в рабочее состояние и показывает причину.

**3.1-R05 · Сбой распознавания виден пользователю** — S — нет
`core/engine.py:120` — у `_listen_worker` есть `finally`, но нет `except`. Состояние очищается, а исключение уносит поток молча: пользователь видит, что «слушаю» погасло, и не понимает, почему ничего не произошло.
*Готово когда:* падение движка распознавания даёт озвученное и записанное в историю сообщение об ошибке.

## Блок U — Отзывчивость интерфейса

**3.1-U01 · Текстовые команды уходят из потока интерфейса** — M — R01
`main_window._on_typed_command` гоняет весь конвейер в потоке интерфейса. Худшую задержку (полное сканирование программ) я убрал в 3.0.0 через `cached_index()`, но `os.startfile`, открытие браузера и обращение к модели по-прежнему выполняются там же. Ответ модели — это секунды полностью замороженного окна.
Решение: обрабатывать так же, как голосовой ввод — в фоновом потоке, с возвратом результата событиями. Событийный канал для этого уже есть.
*Готово когда:* команда с обращением к модели не блокирует окно; индикатор `THINKING` анимируется во время ожидания.

**3.1-U02 · Debounce горячих клавиш** — S — нет
`core/hotkey.py:133` — `_on_triggered` эмитит сигнал без ограничения частоты. Удержание комбинации даёт автоповтор и повторные срабатывания.
Решение: окно подавления (порядка 300 мс) на одну и ту же комбинацию.
*Готово когда:* удержание хоткея вызывает ровно одно срабатывание.

**3.1-U03 · Смена темы и накопление пунктов в трее** — M — нет
Страницы пересоздаются прямо из обработчика сигнала о смене темы — виджет разрушается во время обработки собственного сигнала. Плюс меню трея добавляет `QAction` при каждой перестройке, не убирая старые.
*Готово когда:* десять переключений темы подряд не роняют приложение и не удлиняют меню трея.

**3.1-U04 · Порядок инициализации** — S — нет
`plugin_manager.discover()` вызывается в `main_window.run()` до конструирования `QApplication`. Пока работает, потому что `discover()` только читает манифесты, но любой плагин, тронувший Qt на этом этапе, уронит запуск.
*Готово когда:* до создания `QApplication` не выполняется ни один вызов, способный затронуть Qt.

## Блок P — Разбор фраз

**3.1-P01 · Составная длительность** — S — нет
`voice/reminders.py:68` — `re.search` берёт только **первое** совпадение «число + единица». «Поставь таймер на 1 час 30 минут» превращается в один час, и пользователь узнаёт об этом через полтора часа.
Решение: `re.finditer` и суммирование всех пар, с сохранением существующих ограничений сверху.
*Готово когда:* «1 час 30 минут» даёт 5400 секунд, «2 часа 15 минут 30 секунд» — 8130.

**3.1-P02 · Проценты только по запросу на счёт** — S — нет
Разбор процентов срабатывает раньше проверки на то, что фразу вообще адресовали калькулятору, поэтому обычная реплика с «20 процентов от» перехватывается арифметикой.
*Готово когда:* проценты считаются в счётных фразах и не перехватывают обычную речь.

## Блок L — Наблюдаемость

Единственное, что добавляет в 3.1.0 новое поведение. Обоснование: оба аудита опирались на воспроизведение в песочнице, потому что журналов нет. Без них следующий аудит нечем подкрепить, а после разделения на два процесса отладка вслепую станет невозможной.

**3.1-L01 · Логирование с уровнями** — M — нет
`DEBUG / INFO / WARNING / ERROR`, ротация файлов, разумный размер по умолчанию. Уровень — настройка. Никаких персональных данных в `INFO` и выше: тексты реплик пишутся только на `DEBUG` и только при явном включении.
*Готово когда:* журнал можно приложить к сообщению об ошибке, не раскрывая содержимое разговоров.

**3.1-L02 · Отдельный журнал безопасности** — S — L01
Пишутся события, которые оба аудита искали руками: установка и замена плагина, отклонённое имя плагина, импорт команд (сколько принято, сколько отброшено и почему), запуск системных утилит, обращение к модели по нелокальному адресу, отказ в подтверждении опасного действия.
*Готово когда:* сценарий «подсунуть плагин с чужим идентификатором» виден в журнале без отладчика.

## Решение, а не задача

**3.1-D01 · ADR: граница доверия плагинов** — S — нет
Плагин — произвольный Python в процессе ядра. Ни один блок 4.0.0 или 5.0.0 этого не закрывает: `4.0-H06` описывает, какие разрешения плагин *может запрашивать*, но не мешает ему делать что угодно в обход. К этапу C RinaNeuro, где `N-C05` объявляет весь внешний текст недоверенным, плагин останется единственным путём мимо реестра инструментов, разрешений и подтверждений.
Варианты: оставить как есть с честным предупреждением в интерфейсе и `SECURITY.md`; запуск в отдельном процессе с ограниченным API; полноценная песочница с лимитами ресурсов.
Реализация — **не в 3.1.0**: по объёму это отдельная версия. Здесь принимается только решение и записывается в бэклог.

**РЕШЕНО: отдельный процесс, в 4.0.0.** Записано как `4.0-H07`, сразу за `H03`.
Основание: H03 всё равно переписывает Plugin API с нуля, D02 всё равно проектирует протокол, C04 всё равно заводит каталог разрешений — плагин становится ещё одним клиентом протокола, а не отдельным механизмом. Отложить до 5.0.0 значит менять Plugin API второй раз и мигрировать встроенные плагины дважды.
Полная песочница с лимитами ресурсов отклонена как отдельная исследовательская задача: внутрипроцессной песочницы в Python не существует, а ограничения средствами ОС можно добавить поверх H07 позже, если понадобится.
До 4.0.0 граница описана честно — в `SECURITY.md` и предупреждением при установке.

## Что сознательно не входит

- **Полный переход на SQLite** — 5.0-B01 заводит его для памяти, 4.0-I02 мигрирует данные. Двойная миграция не нужна; в 3.1.0 гонки лечатся блокировкой (R03).
- **Белый список каталогов для целей команд** — ломает portable-программы, ради которых механизм и делался. Защита остаётся прежней: импортированное приходит выключенным и санитизированным.
- **Валидация payload событий по схеме** — это `4.0-D02` и `4.0-D04` (конверт с `correlation_id` и `trace_id`). Оборачивать каждое событие в `{"version": ..., "data": ...}` неправильно: версия согласуется один раз при рукопожатии (`4.0-D03`), а не едет с каждым сообщением. Плагины на шину событий вообще не подписаны.
- **Песочница плагинов** — см. D01, решение здесь, работа позже.

## Порядок работ

1. **L01** — первым, хотя это и не самое срочное: остальные правки проверяются журналом, а не догадками.
2. **S01, S02, S03** — безопасность и честность результата, все мелкие и независимые.
3. **R02, R04, R05** — однострочные и почти однострочные, закрывают залипающие состояния.
4. **R01** — очередь речи, самая крупная в блоке.
5. **R03** — атомарность хранилищ.
6. **U02, U04, P01, P02** — мелкие независимые.
7. **U01, U03** — самые рискованные, делать на уже подстрахованном журналом коде.
8. **S04, L02, D01** — документы и решение.
9. Поднять `APP_VERSION`, дописать раздел 3.1.0 в `CHANGELOG.md`.

Регрессия после каждого блока: конвейер команд, напоминания, плагины, перенос данных, пять языков, пять тем.
